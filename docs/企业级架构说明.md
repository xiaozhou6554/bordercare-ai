# 企业级分层与 Agent 边界

## 分层原则

项目按用户要求使用 **Interface 接口层、Application 应用层、Domain 领域层、Infrastructure 基础设施层**。Agent 是 Application 的编排组件，不另设一个可越权的“万能层”。依赖方向保持向内，领域规则不依赖 Web 框架、外部模型 SDK 或具体缓存实现。

```text
Interface ───────► Application ───────► Domain
                       │                  ▲
                       └──────► Infrastructure
                                      implements Domain ports
```

## 分层职责

### Interface 接口层

`scr/interfaces/http` 接收并验证请求、输出统一 DTO 和 SSE 阶段事件。`scr/interfaces/web` 提供原型指定的市场切换、快捷查询、执行状态、分析卡片、报告与来源信息。`main.py` 提供本地 Web 启动入口和 CLI 命令。

接口层只负责协议、输入校验和展示，不计算业务利润、不访问数据表、不直接请求模型。

### Application 应用层

`ResearchAgent` 实现意图识别与路由，控制完整选品 Pipeline 和单工具流程。九个分析工具通过统一注册表执行。阶段间传递竞品 ASIN；趋势下行或利润未达标时停止后续阶段；单阶段失败记录为失败结果并尽可能继续。

Agent 只允许调用白名单工具，不能绕开领域规则直接修改数据源。Web 的 `/api/research/stream` 消费相同的 Agent 事件，JSON 和 SSE 不维护两套业务实现。

### Domain 领域层

包含分析意图、ToolOutput、ResearchReport 等业务对象和缓存/模型/数据源端口。领域服务提供 FBA 分档成本公式与五维评分。规则可以由单元测试直接调用，不需要启动 FastAPI 或连接外部平台。

### Infrastructure 基础设施层

实现 SQLAlchemy 持久化与版本迁移、Redis/本机缓存、Redis/本机后台队列、LLM 网关和授权数据源适配器。`schema_migrations.py` 在应用启动时执行已登记的迁移；生产配置支持 MySQL 或 PostgreSQL，并要求 Redis、认证和非演示模式。当前本地 Compose 已使用 MySQL 8.4 与 Redis 验证连接和迁移。Redis 队列之外的本机线程仅供开发/单机运行，进程退出时不具备可靠恢复保证。

## 工具输出与证据

每个分析阶段使用统一结构：

```json
{
  "success": true,
  "data": {
    "source": "数据来源",
    "evidence": ["可核对证据"],
    "confidence": "Low",
    "data_timestamp": "UTC 时间",
    "note": "限制与说明"
  },
  "error": null,
  "cached": false
}
```

报告包含每阶段的来源、关键证据、说明、置信度和 UTC 更新时间。低置信度/演示数据不能写成确定性商业结论。

## 运行边界

- 单机本地使用，默认监听 `127.0.0.1:8000`。
- 缓存只在进程内，默认 TTL 为 6 小时。
- LLM Key 从 `.env` 或进程环境变量读取，不写入日志。
- 平台拒绝或无数据时停止尝试，不能绕过反爬限制。
- 登录、组织成员、项目空间、任务、报告版本和证据在配置数据库后启用；供应链、市场和合规数据的准确性仍受授权数据源及其可用性限制。
- 不执行采购、付款或广告操作；合规输出仅作为风险记录并要求人工复核。

## 当前生产边界与差异

- 项目已具备容器化 API/Worker、MySQL/PostgreSQL 与 Redis 运行配置、版本化 schema 迁移、JWT 会话和工作区隔离接口；本地 MySQL/Redis 容器连接及 API/Worker 启动已验收，上线前仍需部署环境做密钥、网络、备份恢复演练和真实平台授权验收。
- Redis Streams 消费组提供消息持久化、确认与 pending reclaim；任务表通过条件更新原子认领，20 秒心跳刷新 120 秒租约，任务超时可由 `TASK_TIMEOUT_SECONDS` 配置，失败最多自动重试 3 次并退避，最终记录脱敏死信元数据。队列统计暴露待处理、pending 和死信数；管理员可查看死信元数据并通过失败任务重试入口重新提交。至少一次投递下的严格 exactly-once 不作承诺；任务执行仍要求工具具备幂等性，目标环境的多 Worker 崩溃故障演练仍待部署验收。
- `scr/infrastructure/container.py` 是唯一 HTTP 运行时组合根。路由只依赖 Application 用例和注入的 RuntimeServices；Domain/Application 不导入 SQLAlchemy、Redis、HTTP SDK 或 FastAPI。API 层只保留协议处理与中间件。
- 可观测性已有请求 ID、脱敏请求日志和健康探针；尚无 OpenTelemetry traces、Prometheus 指标、告警规则和 SLO 面板。
- 安全措施包括长度校验、速率限制、JWT、工作区数据过滤、受限 URL 来源和报告证据规则。不能仅依赖提示词防御所有间接提示注入；外部内容仍按不可信证据处理。
- FR-001 至 FR-018 和企业扩展能力的逐项状态、API/UI、测试证据见 [需求追踪矩阵](requirements-traceability.md)。旧版需求/技术文档将登录、数据库、多租户列为当前版本范围之外；本次用户明确要求扩展这些能力，因此按扩展目标实现并保留原版本范围冲突记录。
