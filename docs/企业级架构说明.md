# BorderCare AI 企业级架构说明

## 一、架构决策

本项目采用：

> 模块化单体（Modular Monolith）+ 清晰的分层与依赖边界

第一阶段先作为一个单体应用运行，保证学习、开发和部署简单；代码按照企业项目的业务边界组织，后续可以根据性能、团队和部署需求拆分服务。

不在一开始强行拆微服务，也不把 MVC、DDD、Agent 等概念全部当成必须使用的模式。

## 二、企业级整体结构

```text
客户端 / 管理后台 / 定时任务
              ↓
        API 接口层
              ↓
        模块化单体应用
        ├── 客服模块
        ├── 订单模块
        ├── 商品与库存模块
        ├── 物流模块
        ├── 知识库模块
        ├── 运营分析模块
        └── 身份、权限与审计模块
              ↓
        基础设施适配器
        ├── 关系数据库
        ├── 向量数据库 / 搜索引擎
        ├── 缓存
        ├── 对象存储
        ├── LLM / Embedding 网关
        └── 外部电商和物流 API
```

## 三、代码目录目标结构

```text
app/
├── interfaces/
│   └── http/                                  # HTTP 路由、请求响应、鉴权、异常处理
├── modules/
│   ├── customer_service/                      # 客服会话、Agent、人工接管
│   │   ├── application/                       # 客服用例和 Agent 编排
│   │   ├── domain/                            # 会话、意图、转人工规则
│   │   └── infrastructure/                   # 模型和工具适配器
│   ├── order/                                 # 订单、支付、退款
│   │   ├── application/                       # 订单查询、取消、退款申请用例
│   │   ├── domain/                            # 订单状态、权限、幂等规则
│   │   └── infrastructure/                   # 订单仓储和支付适配器
│   ├── catalog/                               # 商品与库存
│   ├── logistics/                             # 物流与承运商
│   ├── knowledge/                             # 文档、检索、RAG 评测
│   └── analytics/                             # 运营指标和只读分析
├── shared/                                    # 日志、配置、错误、权限、事件等公共能力
└── infrastructure/                            # 数据库、缓存、向量库、模型和外部 API 适配器
```

当前项目的 `app/application`、`app/domain` 和 `app/infrastructure` 是第 1～4 天的可运行起步结构。随着订单、客服和知识库功能增加，再迁移到上面的业务模块结构。

## 四、各部分职责

### 接口层

只负责接收请求、参数校验、鉴权、调用应用用例和返回响应，不直接写 SQL 或订单规则。

### 应用层

负责完成一个业务用例，例如查询订单、回答政策问题、提交退款申请和转人工。

### Agent

Agent 属于客服模块的应用层，只负责识别意图、选择白名单工具、组织多步骤流程、控制超时和失败重试。

Agent 不能直接决定权限、执行任意 SQL、修改订单状态或绕过人工审核。

### 业务规则层

保存订单状态、权限、退款、库存和人工审核等必须由代码保证的规则。该层不依赖 FastAPI、SQLite 或具体模型 SDK。

### 基础设施层

负责数据库、向量库、缓存、LLM、Embedding、物流 API 和文件存储的具体实现。更换 SQLite、PostgreSQL、云模型或本地模型时，不应修改核心业务规则。

## 五、RAG、LLM 和业务工具的位置

```text
客服模块
  ├── Agent 应用编排
  ├── 调用知识库模块 → RAG 检索
  ├── 调用订单模块 → 订单工具
  └── 调用人工接管模块 → 工单或客服队列

知识库模块
  ├── 文档上传
  ├── 清洗、切分、Embedding
  ├── 向量和关键词检索
  └── 引用、拒答和评测

模型网关
  ├── Mock Client
  ├── 云端 LLM
  ├── 本地模型
  └── vLLM
```

客服模块不能直接操作向量数据库；订单工具不能直接执行模型生成的任意 SQL；模型只能提出建议，最终规则由应用代码执行。

## 六、同步和异步任务

同步请求适合：

- 查询订单、物流和库存
- 知识库问答
- 创建退款申请草稿

异步任务适合：

- 文档解析和向量索引
- 数据同步
- 运营日报
- 批量评测
- 消息和通知发送

本地学习时可以用 Python 后台任务模拟；企业部署时再接入任务队列或消息系统。

## 七、数据与安全边界

- 关系数据库保存订单、用户、支付、库存和审计数据。
- 向量数据库只负责知识检索，不能代替实时订单数据库。
- 模块之间通过应用服务或公开接口协作，不直接访问其他模块的表。
- 退款、改地址、取消订单等高风险操作必须经过幂等校验、用户确认和人工审核。
- 日志记录请求 ID、用户 ID、工具名、结果和耗时。
- 地址、邮箱和支付信息进入日志或模型上下文前必须脱敏。

## 八、演进路线

```text
本地模拟数据
    ↓
模块化单体 + SQLite
    ↓
模块化单体 + PostgreSQL / Redis / 向量库
    ↓
根据实际瓶颈拆分知识库、模型网关或订单服务
```

拆分服务的依据应该是业务边界、团队边界、部署需求和性能瓶颈，而不是为了让项目看起来像微服务。
